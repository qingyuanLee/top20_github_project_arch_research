- [ ] 一、项目回顾
  - [ ] 1. 一句话结论：手工策展的免费公共 REST API 目录，用 Markdown 表格按 ~50 领域分类，标认证/HTTPS/CORS/Postman
  - [ ] 2. 场景问题
    - [ ] 场景一：黑客松/原型开发急需免费数据接口的独立开发者——按 Auth=No、CORS=Yes 10 分钟挑到可直接 fetch 的 API
    - [ ] 场景二：为产品找第三方数据源的后端工程师——CONTRIBUTING 只收有免费额度、不强制购买设备的 API，按认证枚举横向筛选
    - [ ] 场景三：想贡献一个冷门免费 API 的社区成员——照表格模板加一行，发 `Add X API`，CI 自动校验
  - [ ] 3. 组成结构
    - [ ] README.md（约 26 万字节）：商业推荐区 + Index + ~50 领域 Markdown 表
    - [ ] CONTRIBUTING.md：表格 schema、枚举字段值、PR 硬规则、反营销声明
    - [ ] scripts/：validate 校验 + tests 单测 + requirements.txt（带测试套件的清单）
    - [ ] .github/workflows/：3 个 CI（死链检查、格式校验、push/pull 测试）
    - [ ] LICENSE：MIT
  - [ ] 4. 技术组件
    - [ ] 六列表格 schema：API | 描述≤100字 | Auth | HTTPS | CORS | Postman
    - [ ] 枚举闭合：Auth 五选一、CORS 三选一，全表可机读
    - [ ] PR 硬规则：一 PR 一条、标题 Add X API、去 TLD、不以 API 结尾、按字母序
    - [ ] CI 自动死链巡检 + 格式/排序/枚举校验
    - [ ] APILayer 员工 + 社区共同维护，README 顶部有 APILayer 推荐横幅

- [ ] 二、知识沉淀
  - [ ] 1. 前 10 结构性优越点
    - [ ] 组 1（1-5）
      - [ ] 优越点1：表格化 schema 把"能否直接用"变成可过滤维度
        - [ ] 仅凭 CORS=Yes、Auth=No 就判断能否前端直连，信息密度高于纯链接
      - [ ] 优越点2：用 CI 自动校验表格格式与排序
        - [ ] 字母序/列对齐/枚举合法由脚本兜底，人工只判内容价值
      - [ ] 优越点3：死链由 CI 主动巡检
        - [ ] validate_links.yml 自动查数百外链存活，不靠用户举报
      - [ ] 优越点4：反营销、反"购买设备"准入，保住中立性
        - [ ] 首段声明 not a marketing tool，拒收需先买硬件/订阅的 API
      - [ ] 优越点5：枚举字段约束保证全表可机读
        - [ ] 闭合枚举使表格可被脚本解析、二次开发成筛选工具
    - [ ] 组 2（6-10）
      - [ ] 优越点6：描述≤100 字 + 一 PR 一条，控制合并冲突
        - [ ] 短描述保紧凑；一 PR 一条 diff 极小、review 快、冲突少
      - [ ] 优越点7：命名规范（去 TLD、不结尾 API）统一品牌
        - [ ] 全表名称风格一致（Gmail 而非 Gmail.com/Gmail API），便于排序
      - [ ] 优越点8：Postman Run 按钮把"发现"变"即调"
        - [ ] 点 Run in Postman 零配置发真实请求验证可用
      - [ ] 优越点9：跨分类归属有明确仲裁规则
        - [ ] 归入最贴合主用途（Instagram 归 Social），避免重复出现
      - [ ] 优越点10：MIT 许可 + 商业赞助续命
        - [ ] MIT 自由复用，APILayer 赞助提供长期维护人力，比纯志愿可持续
  - [ ] 2. 前 10 优化增强点
    - [ ] 组 1（1-5）
      - [ ] 优化点1：首屏商业横幅过重
        - [ ] 顶部大段 APILayer 推广占首屏；建议压成一条横幅或移到底部 Sponsors
      - [ ] 优化点2：缺少活跃/已死 API 时间维度
        - [ ] 不标最近可用状态；建议 CI 定期 ping，连续失败标 [dead]
      - [ ] 优化点3：无在线搜索/筛选界面
        - [ ] 26 万字节只能 Ctrl-F；建议从 README 生成静态站点按 CORS/Auth/领域筛选
      - [ ] 优化点4：免费额度无量化标注
        - [ ] 只说有免费额度；建议加"1000次/月"列直接判断够不够生产
      - [ ] 优化点5：分类间无标签交叉
        - [ ] 一个 API 只能在一个分类；建议引入标签机制支持跨分类检索
    - [ ] 组 2（6-10）
      - [ ] 优化点6：数据与展示未分离
        - [ ] 数据直接写 README，CI 反向解析 Markdown 校验；建议抽 JSON/YAML 由脚本生成
      - [ ] 优化点7：无用户评价/成功率沉淀
        - [ ] 无稳定性反馈；建议挂 Discussion 或状态页收集使用反馈
      - [ ] 优化点8：CORS=Unknown 项缺乏主动补全
        - [ ] 不少项标 Unknown；建议 CI 发带 Origin 探测请求自动判定
      - [ ] 优化点9：无版本/变更日志视图
        - [ ] API 改版/停服无条目级 changelog；建议记录最近一次验证时间
      - [ ] 优化点10：缺乏非英语社区版本
        - [ ] 仅英文 README；建议提供中/日/西语镜像索引（引用而非整表翻译）
