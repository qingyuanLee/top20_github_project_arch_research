- [ ] 一、项目回顾（TL;DR：声明式组件 UI 库，核心是可中断的 Fiber 渲染工作循环 + 可插拔 host config）
  - [ ] 1. 一句话结论
    - [ ] react-reconciler 用 Fiber 把渲染拆成 render 可中断、commit 一次性提交的工作循环，协调核心与渲染宿主解耦，一套逻辑对接 DOM/Native/Canvas/测试
  - [ ] 2. 场景问题（3 个，≤5）
    - [ ] 场景一：构建交互式 Web UI 的前端工程师——命令式操作 DOM 导致 UI 与状态难同步、bug 难追；用 JSX 声明式描述状态下的 UI
    - [ ] 场景二：需要 SSR/同构的全栈团队——纯客户端渲染首屏白屏、SEO 差；用 react-server / react-dom/server 做 RSC 与服务端渲染
    - [ ] 场景三：跨端/跨渲染目标团队——同一套组件逻辑要跑 DOM、Native、Canvas；靠 react-reconciler + 不同 host config 复用协调核心
  - [ ] 3. 组成结构（5 项，≤5，突出 Fiber）
    - [ ] react 核心（packages/react）：组件契约、hooks、createElement、jsx-runtime，不依赖渲染目标
    - [ ] Fiber 协调核心（packages/react-reconciler）：ReactFiberBeginWork / CompleteWork / WorkLoop 系列 / CommitWork / CommitEffects / ChildFiber / Config
    - [ ] 可插拔 host config：ReactFiberConfig.js 及 WithNoMutation/WithNoPersistence/WithNoHydration 变体，注入 DOM/Native 实际操作
    - [ ] 独立调度（packages/scheduler）：优先级调度、时间切片，与 reconciler 解耦可单独替换
    - [ ] 周边矩阵：react-dom、react-server-dom-*（webpack/parcel/turbopack）、React Compiler（Rust）、shared 特性开关、DevTools 全家桶
  - [ ] 4. 技术组件（5 项，≤5）
    - [ ] 包管理/构建：yarn@1.22.22 workspaces + Rollup 多 release channel（stable/experimental/www-classic/www-modern）
    - [ ] 渲染数据流：mount/update → scheduler 按优先级调度 → render（可中断 beginWork/completeWork）→ commit（不可中断 commitRoot/commitEffects）
    - [ ] 类型与转译：Flow 为主、逐步引入 TypeScript；Babel + Hermes parser
    - [ ] 测试：Jest 30 按 release-channel 分套件；react-test-renderer / noop-renderer 无 DOM 测组件
    - [ ] 自动化：React Compiler（Rust，crates/）构建期自动 memo 化，替代手写 useMemo/useCallback
  - [ ] 5. 验证与客观标注
    - [ ] 证据：stars=250550（API 实时返回）；主语言 JavaScript；B 类（代码架构）
    - [ ] 客观陈述：README 徽章仍指向 legacy facebook/react，GitHub API 当前仓库路径为 react/react；技术事实以 API 实查的 packages/ 结构为准
- [ ] 二、知识沉淀（TL;DR：Fiber 可中断渲染 + host config 解耦 + 独立调度是结构性优势，Yarn/Rollup 老旧与 Flow/TS 双轨是主要维护负担）
  - [ ] 1. 前 10 优越点（第 1 组 1–5，突出 Fiber）
    - [ ] 优越点 1：Fiber 架构把渲染拆成可中断工作单元——render 可被高优先级打断恢复、commit 一次性提交，兼顾帧率与一致性（对比 Stack Reconciler 同步阻塞，让 60fps 成为可能）
    - [ ] 优越点 2：协调核心与渲染宿主解耦（可插拔 host config）——同一 reconciler 对接 DOM/Native/Canvas/测试 noop，一次写逻辑多处渲染
    - [ ] 优越点 3：独立 scheduler 包做优先级调度——时间切片算法内聚，可单独替换/测试
    - [ ] 优越点 4：特性开关（Feature Flags）支撑多 release channel——一套代码按 channel 开关渐进发布，不分叉代码
    - [ ] 优越点 5：React Compiler 把优化从人工迁移到自动——Rust 写编译器自动推导依赖、自动 memo 化
  - [ ] 1. 前 10 优越点（第 2 组 6–10）
    - [ ] 优越点 6：monorepo 工作区 + 多 release channel 构建体系——40+ 包统一版本统一构建、按 channel 裁剪产物
    - [ ] 优越点 7：面向服务端/边缘的 RSC 生态包矩阵——按 webpack/parcel/turbopack 分别适配 server component 序列化
    - [ ] 优越点 8：完善的测试渲染器矩阵——无 DOM 也能测，按 release-channel 分测试套件
    - [ ] 优越点 9：DevTools 与调试工具链一体化——从浏览器扩展到 MCP 调试协议全链路覆盖
    - [ ] 优越点 10：声明式 + 组件化心智模型长期稳定——API 十余年向后兼容、渐进采用，是生态繁荣的结构性原因
  - [ ] 2. 前 10 优化点（第 1 组 1–5）
    - [ ] 优化点 1：构建工具链老旧（Yarn Classic + Rollup 3）——评估迁 Yarn Berry/pnpm + Rollup 4/tsup
    - [ ] 优化点 2：Flow 与 TypeScript 双类型体系并存——向 TS 单体系收敛，降上手成本、统一 IDE
    - [ ] 优化点 3：Fiber 源码文件粒度极细——数十个 ReactFiber*.js 耦合高，在不改内部 API 前提下做模块聚合与注释
    - [ ] 优化点 4：release channel 矩阵带来维护面——收敛通道数量、自动化 channel 差异文档
    - [ ] 优化点 5：React Compiler 生态成熟度——完善迁移文档与增量接入工具，与官方文档深度集成
  - [ ] 2. 前 10 优化点（第 2 组 6–10）
    - [ ] 优化点 6：文档站点与仓库分离的同步——彻底收敛到单一文档站，消除 legacy 链接
    - [ ] 优化点 7：40+ packages 的边界治理——按功能域分组、标注每个包的稳定/实验状态
    - [ ] 优化点 8：错误码与告警的可操作性——错误信息直接附交互式排查链接与修复建议
    - [ ] 优化点 9：服务端组件在多 bundler 间一致性——抽象 bundler 适配层，减少重复实现
    - [ ] 优化点 10：对 AI 编码助手的适配——系统化提供架构索引与贡献者 AGENTS.md，降低 AI 生成 PR 的理解成本
